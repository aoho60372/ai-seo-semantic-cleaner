WORKFLOW ДЛЯ ОБРАБОТКИ SEO-СЕМАНТИКИ
=====================================

Расположение проекта:

E:\AI\seo


НАЗНАЧЕНИЕ
==========

Проект предназначен для многократной обработки семантических ядер:

- очистки запросов;
- разделения на коммерческие, информационные и нерелевантные;
- семантической кластеризации;
- проверки результатов языковой моделью;
- исправления сомнительных решений;
- сохранения проверенных знаний между заданиями;
- работы с разными тематиками без зашитых в Python словарей.

Workflow гибридный:

- языковая модель принимает SEO-решения с учётом конкретной тематики;
- Python выполняет массовые, воспроизводимые вычисления;
- модель анализирует результат и исправляет слабые решения;
- проверенные знания могут помогать в следующих заданиях той же тематики.

Python не заменяет модель, а является её вычислительным исполнителем.


ПОД КАКОЙ HARNESS РАССЧИТАН ПРОЕКТ
=================================

Проект рассчитан на LM Studio Bionic в режиме CODE PROJECT.

Необходимая настройка Bionic:

1. Создать или открыть Code Project.
2. Выбрать E:\AI\seo в качестве рабочей папки.
3. Использовать модель, которая надёжно выполняет инструкции и умеет вызывать
   инструменты терминала и файловой системы.
4. Для каждого отдельного семантического ядра создавать новую сессию Bionic.

Не следует использовать Bionic Work Project для этого workflow.

Причины:

- Code Project имеет доступ к выбранной локальной папке и терминалу;
- Work Project обычно использует управляемую песочницу для документов;
- встроенный инструмент Bionic run_python работает в ограниченной среде
  Pyodide и не видит проектную .venv и установленные ML-библиотеки.

Bionic должна автоматически читать файл AGENTS.md из корня проекта.
AGENTS.md является основной инструкцией для модели.

В корне проекта разрешены только поддерживаемые Python-файлы:

- seo_workflow.py;
- seo_prepare.py;
- seo_pipeline.py;
- seo_knowledge.py.

Модель не должна создавать check_excel.py, convert_to_csv.py, run_prepare.py,
*_robust.py или любые другие одноразовые Python-скрипты. Если штатный workflow
не поддерживает структуру входного файла, модель должна остановиться и сообщить
точную ошибку. Временные данные разрешены только в jobs\<job>\tmp или
jobs\<job>\cache.


PYTHON-ОКРУЖЕНИЕ
================

Интерпретатор проекта:

E:\AI\seo\.venv\Scripts\python.exe

Базовая версия Python, на которой создавалась среда:

Python 3.14

Зависимости перечислены в:

E:\AI\seo\requirements.txt

Основные библиотеки:

- pandas;
- openpyxl;
- scikit-learn;
- sentence-transformers;
- umap-learn;
- hdbscan.

Проверка окружения:

.\.venv\Scripts\python.exe -c "import pandas, sklearn, sentence_transformers, umap, hdbscan, openpyxl; print('READY')"

Установка или восстановление зависимостей:

.\.venv\Scripts\python.exe -m pip install -r requirements.txt

Все embeddings и кластеризация выполняются на CPU.

GPU намеренно оставлена локальной языковой модели Bionic.

Не следует переводить sentence-transformers на CUDA, если эта политика не была
осознанно изменена и на видеокарте нет достаточного запаса VRAM.

При первом реальном запуске sentence-transformers может потребоваться доступ
в интернет для загрузки embedding-модели. Последующие запуски используют
локальный кэш.

ЗАПУСК ЧЕРЕЗ HERMES
===================

Основной harness для проекта — Hermes. Его терминал настроен на E:\AI\seo,
а SEO workflow вызывается через PowerShell-обёртку seo.ps1. Начинать задачу
нужно обычным запросом с именем файла и тематикой; Hermes самостоятельно
вызывает next и получает единственный допустимый следующий шаг.

Подробный короткий протокол находится в HERMES.md. Не нужно вручную запускать
Python, pip, Excel-обработчики или читать временные JSON-файлы.


СТАРЫЙ ЗАПУСК ИЗ BIONIC ЧЕРЕЗ POWERSHELL
========================================

Встроенный shell Code Project на Windows использует Git Bash. Поэтому Bionic
не должна напрямую выполнять команды вида:

.\.venv\Scripts\python.exe

Для Bionic создан постоянный PowerShell-обёртчик:

E:\AI\seo\seo.ps1

Из-за особенности Windows PowerShell 5.1 многословные UTF-8 аргументы нельзя
надёжно передавать ему напрямую через параметр -File из Git Bash. Поэтому
Bionic вызывает небольшой транспортный мост:

E:\AI\seo\seo-bionic.sh

Он не выполняет SEO-логику в Bash. Он только сохраняет границы аргументов и
сразу передаёт управление seo.ps1.

Он:

- запускает проектный .venv;
- устанавливает UTF-8 для PowerShell и Python;
- отключает лишние progress bars и предупреждения;
- всегда начинает работу из E:\AI\seo;
- возвращает Bionic настоящий код завершения workflow.

Все рабочие команды Bionic должны начинаться одинаково:

./seo-bionic.sh

Главная команда для самой Bionic — не status и не ручной поиск файлов, а:

./seo-bionic.sh next --input "input-file.xlsx" --topic "тема ядра" --quiet

Она читает state.json и возвращает следующий разрешённый шаг. После сжатия
контекста, ошибки инструмента или нового сообщения Bionic должна вызывать next
снова. После подготовки можно указывать --job "<job>" вместо --input и
--topic. Команда может вернуть stop: это означает, что запуск уже завершён и
искать «другой» файл или запускать очистку повторно нельзя.

Пример:

./seo-bionic.sh status --job "<job>" --compact --quiet

Пользователь при ручной работе в обычном PowerShell по-прежнему может запускать
.\seo.ps1 напрямую.

ГЛАВНЫЙ ПРИНЦИП
===============

Python-скрипты не содержат фиксированных словарей для автозапчастей, вакансий,
медицины, недвижимости или другой конкретной тематики.

Для каждого нового задания модель должна понять:

- тематику;
- границы бизнеса;
- что является коммерчески полезным;
- что является информационным;
- что является нерелевантным мусором;
- какие неоднозначные случаи требуют проверки.

Знания конкретного задания хранятся в:

- jobs\<job>\job_config.json;
- jobs\<job>\model_labels.xlsx;
- базе проверенных знаний.

Общие Python-скрипты должны оставаться независимыми от тематики.


ЧТО СООБЩАТЬ BIONIC
===================

Минимальный запрос:

Обработай файл "input-file.xlsx".
Тематика: автозапчасти.

Более качественный запрос:

Обработай файл "input-file.xlsx".
Тематика: запчасти для японских легковых автомобилей.
Сайт продаёт новые и контрактные запчасти.
Услуги ремонта не входят в тематику.
Информационные запросы можно сохранить для будущего блога.
Запросы по конкурентам и маркетплейсам сначала вынеси на проверку и не удаляй
автоматически.

Полезно сообщать:

- какие товары и услуги входят в бизнес;
- что явно не входит;
- целевую аудиторию;
- регион;
- новые, подержанные, оптовые, розничные товары или услуги;
- нужны ли информационные материалы;
- как относиться к конкурентам и маркетплейсам;
- ограничения по брендам, моделям, профессиям и категориям.

Модель должна задавать дополнительные вопросы только тогда, когда ответ
существенно изменяет релевантность или структуру кластеров.


ПОЛНЫЙ РАБОЧИЙ ПРОЦЕСС
======================

ЭТАП 1. ПОМЕСТИТЬ ИСХОДНЫЙ ФАЙЛ В files\
------------------------------------------------

Пример:

E:\AI\seo\files\auto-parts-july.xlsx

Исходный файл никогда не должен перезаписываться.


ЭТАП 2. ПОДГОТОВИТЬ ЗАДАНИЕ
---------------------------

Команда:

./seo-bionic.sh prepare "auto-parts-july.xlsx" --topic "автозапчасти"

Полезные параметры:

--sample-size 500
    Размер таблицы для модельной разметки.

--phrase-column "Поисковый запрос"
    Точное название колонки с фразами, если автоматика ошибается.

--frequency-column "Частотность"
    Точное название колонки частотности, если автоматика ошибается.

--job-name "auto-parts-july"
    Стабильное имя папки задания.

--reuse-topic auto
    Автоматически использовать знания текущей тематики. Это значение по
    умолчанию.

--reuse-topic "контрактные автозапчасти"
    Явно использовать знания близкой тематики.

--reuse-topic none
    Не использовать старые знания.

--prior-limit 150
    Максимальное количество старых примеров до применения ограничения в одну
    треть выборки.

Команда prepare создаёт:

jobs\<job>\inspection.json
jobs\<job>\model_labels.xlsx
jobs\<job>\job_config.json
jobs\<job>\state.json

state.json — короткое сохранённое состояние задания. После сжатия контекста,
перезапуска Bionic или новой сессии она должна прочитать именно этот файл и
продолжить с указанного этапа, а не пытаться восстановить историю из чата.


ЭТАП 3. ИЗУЧИТЬ И РАЗМЕТИТЬ ВЫБОРКУ
------------------------------------

Модель не должна печатать или читать model_labels.xlsx через терминал: это
создаёт большой контекст и может испортить кириллицу. Вместо этого используются
ограниченные JSON-пакеты:

./seo-bionic.sh sample --job "<job>" --offset 0 --limit 25 --quiet

Каждая строка имеет стабильный id. Bionic передаёт до 25 решений напрямую,
без фраз и без создания большого JSON-файла:

./seo-bionic.sh apply-labels-inline --job "<job>" --labels "row-000001|commercial|0.95;row-000002|garbage|0.98" --quiet

Ответ отдельно показывает new, updated и unchanged. Если new равно 0,
модель вызывает next и не повторяет тот же пакет.

После первых 100–150 разнородных решений Python выбирает только неуверенные
строки для следующей итерации:

./seo-bionic.sh review --job "<job>" --limit 20 --quiet

Так модель принимает тематические SEO-решения, а Python выполняет расчёты.
Не требуется искусственно помечать реальные фразы как garbage: этот класс
опционален и используется только при наличии настоящего нерелевантного спроса.

Для запуска после разметки используйте автоматический выбор режима:

./seo-bionic.sh run-auto "input-file.xlsx" --job "<job>" --quiet

Команда берёт число уникальных фраз из inspection.json. Если их меньше 100 000,
запускается обычный workflow. При 100 000 и более выбирается chunked large-mode.
Большой XLSX не запускается рискованно: workflow попросит экспортировать его в
CSV/TSV и затем повторить run-auto. Порог можно изменить параметром
--large-threshold 150000.

model_labels.xlsx содержит репрезентативную смесь:

- высокоприоритетных и высокочастотных фраз;
- длинных фраз;
- случайных фраз;
- представителей разных лексических групп;
- количества дублей;
- старых проверенных примеров, если они существуют.

Модель заполняет колонку Model Label только одним из значений:

commercial
informational
garbage

Для каждой размеченной строки обязательно заполняется:

Model Confidence

Значение Model Confidence должно быть числом от 0 до 1.

Для неоднозначных решений и всех значений confidence ниже 0,7 обязательно
заполняется:

Model Notes

Рекомендуемый объём:

- 300–500 проверенных фраз для обычного задания;
- достаточное количество представителей всех трёх классов;
- больше примеров для широкой или неоднозначной тематики.

Минимум для supervised-режима:

- не менее 100 корректных меток или вся выборка, если в ней меньше 100 строк;
- не менее 10 примеров каждого из трёх классов;
- корректный Model Confidence у каждой размеченной строки;
- проверены 50 наиболее приоритетных строк.

Если условия не выполнены, run блокируется. Обходить проверку через отдельный
скрипт запрещено.


ЭТАП 4. ЗАПОЛНИТЬ КОНФИГУРАЦИЮ ЗАДАНИЯ
---------------------------------------

Модель редактирует:

jobs\<job>\job_config.json

Основные поля:

topic.relevant_seeds
    Реалистичные фразы, однозначно относящиеся к тематике.

topic.garbage_seeds
    Реалистичные нерелевантные фразы, которые могут встретиться в исходнике.

intent.commercial_seeds
    Коммерческие или целевые фразы для этой конкретной тематики.

intent.informational_seeds
    Информационные, исследовательские и проблемные фразы.

positive_markers и garbage_markers
    Необязательные высокоточные переопределения. Их следует использовать
    осторожно.

commercial_markers и informational_markers
    Необязательные высокоточные маркеры интента.

minimum_relevance и garbage_probability
    Пороги определения мусора. Ошибочное удаление релевантной фразы опаснее,
    чем отправка сомнительной фразы на проверку.

clustering.n_neighbors
    Более высокое значение создаёт более широкую семантическую структуру.

clustering.min_cluster_size
    Минимальный размер кластера HDBSCAN.

clustering.review_threshold
    Порог уверенности кластера для попадания в Human review.

cluster_stop_words
    Тематические слова, которые не должны доминировать в названиях кластеров.

Рекомендация:

Использовать 15–30 разнообразных естественных фраз каждого класса, когда это
возможно. Не ограничиваться отдельными общими словами.


ЭТАП 5. ПРОВЕРИТЬ ГОТОВНОСТЬ
----------------------------

Команда:

./seo-bionic.sh status --job "<job>"

Важные поля:

ready_for_supervised_run
labeled_counts
config_exists
seed_counts
label_quality
unexpected_python_files
blocking_errors
warnings

Полный запуск разрешён только при:

ready_for_supervised_run = true

Перед продолжением необходимо исправить каждый пункт из blocking_errors.
Предупреждения warnings также нужно проверить вручную.

Блокирующими считаются:

- менее 100 проверенных строк;
- менее 10 примеров любого класса;
- пустой или некорректный Model Confidence;
- неподдерживаемые значения Model Label;
- непроверенные высокоприоритетные строки;
- более 50% garbage в размеченной выборке;
- garbage, противоречащий relevant seeds или positive markers;
- менее пяти seeds в каждом обязательном списке;
- посторонние Python-файлы в корне проекта.

Доля garbage выше 35% создаёт предупреждение и требует ручной проверки риска
ложного мусора.


ЭТАП 6. ЗАПУСТИТЬ ПОЛНУЮ ОБРАБОТКУ
-----------------------------------

Команда:

./seo-bionic.sh run "auto-parts-july.xlsx" --job "<job>"

Результаты версионируются:

outputs\<job>\auto-parts-july_run_001.xlsx
outputs\<job>\auto-parts-july_run_002.xlsx

Старые запуски не перезаписываются.

Итоговая книга содержит:

Commercial clusters
Informational clusters
Garbage
Cluster review
Human review
Quality report
Validation metrics
Run configuration


ЭТАП 7. ПРОВЕРИТЬ КАЧЕСТВО
---------------------------

Validation metrics содержит:

- accuracy на отложенной выборке;
- precision каждого класса;
- recall каждого класса;
- F1 каждого класса;
- confusion matrix;
- количество валидационных примеров.

Эти метрики показывают согласованность с разметкой модели, но не доказывают
идеальную SEO-корректность в реальном поиске.

Cluster review содержит:

- интент;
- автоматически созданное имя кластера;
- количество фраз;
- суммарную частотность;
- среднюю уверенность классификации;
- среднюю вероятность кластера;
- репрезентативные фразы;
- поля для нового названия, действия модели и комментариев.

Human review содержит:

- низкую уверенность классификации;
- некластеризованные фразы;
- низкую вероятность кластера;
- потенциально ошибочный мусор;
- Correct Intent;
- Correct Cluster;
- Reviewer Notes.

Модель обязана проверить:

- высокочастотные кластеры;
- риск ложного мусора;
- смешение разных сущностей;
- смешение коммерческого и информационного интента;
- дублирующиеся или слишком широкие кластеры;
- чрезмерную долю Unclustered.

Первый запуск не считается автоматически финальным.


ЭТАП 8. ИМПОРТИРОВАТЬ ИСПРАВЛЕНИЯ
----------------------------------

После заполнения Correct Intent в Human review:

./seo-bionic.sh feedback "./outputs/<job>/reviewed-result.xlsx" --job "<job>"

Исправленные примеры добавляются обратно в model_labels.xlsx.

Если ошибка систематическая, модель также корректирует job_config.json и
повторяет ЭТАП 6.


ЭТАП 9. СОХРАНИТЬ ПРОВЕРЕННЫЕ ЗНАНИЯ
-------------------------------------

С проверенной книгой:

./seo-bionic.sh learn --job "<job>" --reviewed-workbook "./outputs/<job>/reviewed-result.xlsx"

Без отдельной проверенной книги:

./seo-bionic.sh learn --job "<job>"

Сохраняются только:

- размеченные моделью примеры;
- исправленные строки из review;
- профиль и конфигурация тематики;
- уверенность, источник задания и уровень проверки.

Автоматические предсказания для всего массива не сохраняются как знания.

Причина:

Слепое обучение на всех собственных предсказаниях создаёт confirmation bias и
накапливает ошибки.


ЭТАП 10. СОЗДАТЬ ФИНАЛЬНЫЙ ФАЙЛ
--------------------------------

Когда модель закончила обязательную проверку качества и выбрала принятый
версионированный запуск, она обязана создать стабильный итоговый файл:

./seo-bionic.sh finalize "auto-parts-july.xlsx" --job "<job>"

По умолчанию команда берёт запуск с самым большим номером и создаёт:

outputs\<job>\auto-parts-july_FINAL.xlsx

Если модель вручную исправляла отдельную проверенную книгу, её нужно указать
явно:

./seo-bionic.sh finalize "auto-parts-july.xlsx" --job "<job>" --source "./outputs/<job>/reviewed-result.xlsx"

Команда finalize:

- проверяет наличие обязательных листов результата;
- сохраняет исходную проверенную книгу;
- не удаляет и не перезаписывает файлы run_001, run_002 и другие версии;
- атомарно создаёт или обновляет один понятный файл *_FINAL.xlsx;
- не должна запускаться до завершения проверки качества.

Если предыдущий *_FINAL.xlsx обновлён, его источник всё равно остаётся среди
версионированных запусков или в явно указанной проверенной книге.


ЭТАП 11. УДАЛИТЬ ВРЕМЕННЫЕ ФАЙЛЫ
---------------------------------

Команда:

./seo-bionic.sh cleanup --job "<job>"

Cleanup может удалять только:

- jobs\<job>\tmp;
- jobs\<job>\cache;
- файлы .tmp и .part внутри текущего задания;
- lock-файлы Excel внутри текущего задания;
- корневой и job-local __pycache__.

Cleanup не должен удалять:

- исходники из files\;
- job_config.json;
- model_labels.xlsx;
- inspection.json;
- базу знаний;
- outputs;
- проверенные итоговые книги;
- что-либо внутри .venv.


КАК РАБОТАЕТ НАКОПЛЕНИЕ ЗНАНИЙ
==============================

База:

E:\AI\seo\knowledge\seo_knowledge.sqlite3

Просмотр всех тематик:

./seo-bionic.sh knowledge

Просмотр одной тематики:

./seo-bionic.sh knowledge --topic "автозапчасти"

При повторном использовании тематики:

- старые примеры балансируются между commercial, informational и garbage;
- старые примеры занимают не более одной трети таблицы разметки;
- остальные строки берутся из нового ядра;
- старые строки помечаются как prior knowledge;
- модель обязана перепроверить их относительно новых границ бизнеса;
- старая конфигурация является стартовой точкой, а не окончательной истиной.

Старые знания должны помогать, но не быть единственным основанием решения.

Удаление одной тематики выполняется только после явного разрешения пользователя:

./seo-bionic.sh forget --topic "автозапчасти" --confirm "автозапчасти"

Подтверждение должно точно совпадать с нормализованным ключом, который показывает
команда knowledge. Модель не должна вызывать forget при обычной уборке.

ОГРАНИЧЕНИЯ
===========

1. Семантическая кластеризация не равна SERP-кластеризации
----------------------------------------------------------

sentence-transformers группирует фразы по смыслу.

Для определения посадочных страниц иногда нужно сравнивать URL в поисковой
выдаче. Две семантически близкие фразы могут требовать разные страницы, а две
лексически разные — иметь почти одинаковый SERP.

Для важных коммерческих кластеров может потребоваться проверка поисковой выдачи.


2. Очень большие массивы
-------------------------

Один лист Excel не может содержать десять миллионов строк. Лимит листа Excel —
1 048 576 строк.

Стандартный workflow загружает данные в память и использует UMAP/HDBSCAN. Он
подходит для умеренных ядер, например около 50 тысяч фраз, но не является
движком обработки десяти миллионов строк.

Для больших CSV/TSV теперь есть отдельный режим:

./seo-bionic.sh run-large "semantic.csv" --job "<job>" --chunk-size 50000 --quiet

Он читает данные частями на CPU, сохраняет полный результат в
outputs\<job>\large\<input>\parts\part-*.csv.gz, создаёт manifest.json,
uncertain_review.csv, cluster_summary.csv и небольшой
<input>_LARGE_SUMMARY.xlsx. Кластеризация выполняется на детерминированной
репрезентативной выборке MiniBatchKMeans; остальные фразы получают ближайший
центроид. Это не SERP-кластеризация и не глобальный UMAP/HDBSCAN.

Для многомиллионных ядер остаются важны ограничения:

- CSV, Parquet, база данных или набор файлов;
- потоковое чтение чанками;
- reservoir sampling из нового массива;
- старые знания как warm start;
- пакетная классификация;
- иерархическая или coarse-кластеризация;
- партиционированные результаты вместо одной книги Excel.

Постоянные знания помогают run-large как стартовая размеченная выборка, но
обычную команду run нельзя использовать для многомиллионных файлов.


3. Самообучение намеренно ограничено
-------------------------------------

Workflow не дообучает языковую модель и не fine-tune'ит sentence-transformer.

Под "обучением" понимается:

- накопление проверенных размеченных примеров;
- сохранение конфигураций тематик;
- обучение нового лёгкого классификатора для каждого задания;
- ограниченное использование старых проверенных примеров.

Это безопаснее и прозрачнее, чем обучение на всех автоматических предсказаниях.


4. Производительность CPU
--------------------------

Embeddings выполняются на CPU, потому что GPU занята Bionic-моделью.

Большие задания могут выполняться долго. batch_size можно менять в
job_config.json, но увеличение значения повышает потребление RAM.
