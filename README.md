# AI SEO Semantic Cleaner

Локальный workflow для очистки, классификации и кластеризации семантических
ядер с участием текстовой языковой модели.

Система принимает XLSX, CSV или TSV, отделяет коммерческие запросы от
информационных и нерелевантных, группирует релевантные фразы по смысловым
кластерам, формирует компактный Excel и сохраняет ручные исправления как
знания темы.

Workflow не привязан к конкретной LLM или поставщику. Можно использовать любую
локальную или облачную текстовую модель, если агентный
harness умеет выполнять команды в терминале, передавать модели их результат и
продолжать многошаговую задачу. Готовая интеграция в этом репозитории
предназначена для Hermes; другой агентный harness может работать с тем же
контроллером `seo_workflow.py`.

## 1. Что умеет проект

- автоматически находит колонку поисковых запросов;
- читает XLSX, CSV и TSV;
- распознаёт UTF-8, UTF-8 BOM, CP1251 и CP866;
- не разрушает одноколоночные CSV, в запросах которых встречаются запятые;
- удаляет пустые строки и объединяет нормализованные дубли;
- использует тему и границы бизнеса, заданные пользователем;
- размечает только ограниченную репрезентативную выборку через текстовую LLM;
- применяет active learning: отдаёт LLM прежде всего неоднозначные и
  противоречивые фразы;
- отдельно определяет релевантность теме и коммерческий/информационный интент;
- использует локальную multilingual E5 embedding-модель;
- объединяет смысловые embeddings и символьные TF-IDF-признаки;
- обучает лёгкие классификаторы scikit-learn на метках текущей задачи;
- калибрует порог отделения мусора, если реальных примеров достаточно;
- автоматически выбирает обычный или крупномасштабный режим;
- кластеризует коммерческие и информационные запросы отдельно;
- создаёт очередь `Human review` размером не более 300 строк для ручной
  проверки;
- сохраняет состояние задачи на диске и продолжает работу после нового чата;
- защищает длительный этап от повторного параллельного запуска;
- пишет подробный прогресс в журнал, а LLM возвращает компактный JSON;
- командой `/sknow` импортирует ручные исправления без повторной чистки и
  автоматически связывает проверенный Excel с правильной job;
- сохраняет тематические профили, метки модели и подтверждённые человеком
  примеры в локальной SQLite-базе;
- использует накопленные знания как вспомогательные данные следующих задач той
  же темы, не дообучая LLM или embedding-модель;
- удаляет известные временные файлы и embedding-кэш.

## 2. Быстрый запуск

### 2.1. Подготовьте файл

Поместите исходник в `files/`.

Поддерживаемые форматы:

- `.xlsx`;
- `.csv`;
- `.tsv`.

Автоматически распознаются колонки:

- `Поисковый запрос`;
- `query`;
- `keyword`;
- `phrase`;
- `фраза`;
- `запрос`.

Регистр не учитывается. Если подходящей колонки нет, можно указать её вручную
через низкоуровневую команду `prepare --phrase-column`.

Частотность определяется по названию, содержащему `частот`, `показы`,
`frequency` или `volume`. Частотность необязательна.

### 2.2. Запустите очистку

Общий синтаксис:

```text
/sclear <имя_файла> <тематика и бизнес-границы>
```

Пример:

```text
/sclear semantic.xlsx Продажа автомобильных запчастей
```

Чем точнее описана тема, тем лучше LLM сможет отделить полезную семантику от
лексически похожего мусора. Желательно указать:

- что продаётся или продвигается;
- целевую аудиторию;
- географию;
- нужны ли информационные запросы;
- важные исключения;
- границы между соседними тематиками.

После запуска не требуется писать «продолжи». Hermes выполняет замкнутый цикл,
а длительный Python-этап запускается один раз в фоне и продолжает работу после
уведомления терминала.

### 2.3. Найдите результат

Всегда ориентируйтесь на поле `output` финального JSON.

Типичные места:

- стандартный режим: `outputs/<исходное_имя>_clustered.xlsx`;
- крупный режим:
  `outputs/<job>/large/<исходное_имя>/<исходное_имя>_clustered.xlsx`.

### 2.4. Проверьте результат вручную

Откройте итоговый XLSX и проверьте:

- несколько крупных коммерческих кластеров;
- несколько информационных кластеров;
- случайную выборку из `Garbage`;
- все строки `Human review`.

В `Human review` заполните `Correct Intent` только там, где хотите сохранить
исправление. Допустимые значения:

- `commercial`;
- `informational`;
- `garbage`.

При необходимости добавьте пояснение в `Reviewer Notes`. Не меняйте остальные
служебные столбцы и лист `_Workflow`: его `Workflow Job ID` связывает книгу с
правильной job даже при наличии нескольких завершённых задач.

Сохраните проверенную книгу и поместите её в `files/`.

### 2.5. Добавьте исправления в базу знаний

Общий синтаксис:

```text
/sknow <проверенный_файл.xlsx>
```

Пример:

```text
/sknow semantic_clustered_reviewed.xlsx
```

Команда `/sknow`:

1. проверяет наличие указанного XLSX в `files/`;
2. читает `Workflow Job ID` из листа `_Workflow`;
3. находит соответствующую папку `jobs/<job>/`;
4. импортирует только строки с заполненным `Correct Intent`;
5. переносит исправления в рабочий `model_labels.xlsx`;
6. сохраняет профиль темы, модельные метки и исправленные человеком примеры в
   `knowledge/seo_knowledge.sqlite3`;
7. возвращает количество обработанных модельных и исправленных примеров;
8. переводит задачу в состояние `knowledge_saved`;
9. не запускает повторную чистку, классификацию или кластеризацию.

Это не fine-tuning текстовой LLM и не дообучение E5. При следующем запуске с
тем же нормализованным ключом темы workflow подмешивает до 150 сбалансированных
примеров как вспомогательные обучающие данные. Прежние решения не имеют
безусловного приоритета над новой выборкой.

До успешного `/sknow` не удаляйте `jobs/<job>/`: без неё workflow не сможет
связать проверенную книгу с исходной задачей. После успешного импорта итоговый
XLSX останется в `outputs/`, знания — в SQLite, а job можно оставить для аудита,
архивировать или удалить, если повторный импорт и диагностика больше не нужны.

## 3. Как разделена работа между LLM и Python

Текстовая LLM и локальные Python-компоненты решают разные задачи.

### Текстовая LLM

LLM:

- понимает описание тематики и бизнес-границы;
- размечает короткие пакеты как `commercial`, `informational` или
  `garbage`;
- определяет смысл частотных лексических семейств;
- формирует тематические коммерческие, информационные и отрицательные
  прототипы;
- проверяет пограничные примеры;
- в крупном режиме оценивает релевантность кластеров и отдельных подозрительных
  представителей.

Весь исходный файл в контекст LLM не помещается. Модель видит только небольшие
JSON-пакеты. Поэтому 100 тысяч или несколько миллионов строк не требуют
контекста соответствующего размера.

### Локальный Python

Python:

- читает и нормализует исходник;
- строит репрезентативную выборку;
- считает embeddings всех фраз;
- обучает классификаторы;
- массово классифицирует строки;
- вычисляет вероятности и пороги;
- выполняет кластеризацию;
- выбирает наиболее полезные строки для следующего обращения к LLM;
- хранит состояние, журналы и знания;
- создаёт итоговый Excel.

Такой подход сохраняет смысловые возможности LLM, но не расходует её токены на
сотни тысяч однотипных решений.

## 4. Системные требования

### Обязательные компоненты

- Windows 10 или Windows 11;
- PowerShell 5.1 либо PowerShell 7;
- Git;
- Python 3.11 рекомендуется;
- SSD;
- текстовая LLM в агентном harness;
- локальная embedding-модель `multilingual-e5-base` или
  `multilingual-e5-small`.

Текущая конфигурация зависимостей проверена с Python 3.11. Использование совсем
новой версии Python может быть невозможно, пока для PyTorch, HDBSCAN или UMAP
не опубликованы совместимые бинарные пакеты.

### Требования к текстовой модели

Проект не проверяет название или поставщика LLM. Подойдёт любая текстовая
модель, которая:

- уверенно следует инструкциям;
- поддерживает tool calling или управление терминалом через harness;
- возвращает структурированные короткие решения;
- способна различать тематику, релевантность и поисковый интент;
- не завершает многошаговую задачу после каждого пакета.

Практические настройки:

- temperature: примерно `0.0–0.2`;
- контекст: от 20 тысяч токенов, комфортнее около 50 тысяч (если семантика от 400 тыс. фраз, то контекст увеличится примерно до 150 тысяч);
- reasoning: средний или высокий для сложных тематик;
- vision не требуется.

LLM может быть облачной или локальной. Если она облачная, выбранные для
разметки фразы передаются поставщику модели. Полный файл, embeddings,
классификаторы и кластеризация остаются локальными. Для конфиденциальной
семантики используйте локальную LLM.

### CPU-режим

GPU не является обязательной.

Практический минимум:

- современный четырёхъядерный процессор;
- 16 ГБ RAM;
- 10 ГБ свободного места.

Рекомендуется:

- 8 и более физических ядер;
- 32 ГБ RAM;
- быстрый NVMe SSD.

На CPU embeddings будут считаться заметно дольше. UMAP, HDBSCAN,
MiniBatchKMeans, pandas и scikit-learn в текущем workflow всё равно в основном
используют CPU, поэтому CUDA ускоряет не абсолютно все этапы.

### CUDA-режим

Для ускорения embeddings:

- NVIDIA GPU;
- актуальный драйвер NVIDIA, совместимый с CUDA 12.8 wheel;
- около 4 ГБ свободной VRAM как практический минимум для
  `multilingual-e5-base`;
- 8 ГБ и более свободной VRAM рекомендуется.

Отдельная установка CUDA Toolkit обычно не нужна: необходимые runtime-библиотеки
поставляются wheel-пакетом PyTorch. Проверять нужно не наличие CUDA Toolkit, а
результат `torch.cuda.is_available()`.

Если локальная LLM уже занимает почти всю видеопамять, embedding-модель может
получить ошибку нехватки VRAM. В таком случае:

- освободите часть VRAM;
- уменьшите `embedding_batch_size`;
- либо задайте `"embedding_device": "cpu"` в конфигурации конкретной
  задачи.

### Требования в зависимости от размера ядра

| Размер после нормализации | Стратегия | Практические ресурсы |
|---|---|---|
| До 500 фраз | LLM размечает все уникальные строки | 8–16 ГБ RAM, CPU допустим |
| 501–5 000 | Active learning с уменьшенными аудитами | 16 ГБ RAM |
| 5 001–99 999 | Полный стандартный режим, UMAP + HDBSCAN | 32 ГБ RAM рекомендуется |
| От 100 000 | Потоковый крупный режим, части по 50 000 | 32 ГБ RAM и быстрый SSD |
| Миллионы строк | Тот же крупный режим, но больше диска и времени | 32–64 ГБ RAM, NVMe, CUDA желательна |

Граница в 100 000 настраивается параметром `--large-threshold`, но стандартное
значение выбрано для ограничения памяти. Для больших CSV число уникальных фраз
на подготовительном этапе оценивается консервативно по непустым строкам, поэтому
workflow может выбрать безопасный крупный режим раньше.

Для крупного режима резервируйте место не только под исходник, но и под
сжатые части, сводки, Excel и временные embeddings. Разумный ориентир —
несколько размеров исходного файла.

В выводе remote должен быть адрес этого репозитория. Все дальнейшие команды

Пустые и генерируемые каталоги не хранятся в Git, поэтому после клонирования

```powershell

py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip setuptools wheel
```

Если команда `py -3.11` недоступна, укажите установленный Python 3.11:

```powershell
python -m venv .venv
```

Важно: Hermes и ручные команды должны использовать именно
`.\.venv\Scripts\python.exe`, а не системный Python.

### 5.4. Установка зависимостей: CPU

Для гарантированного CPU-варианта сначала установите CPU-сборку PyTorch, затем
остальные библиотеки:

```powershell
.\.venv\Scripts\python.exe -m pip install torch --index-url https://download.pytorch.org/whl/cpu
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

### 5.5. Установка зависимостей: NVIDIA CUDA

Для CUDA:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install --upgrade -r requirements-cuda.txt
```

`requirements-cuda.txt` устанавливает зафиксированную CUDA-сборку PyTorch.
Если используемая видеокарта или драйвер не поддерживает указанную сборку,
подберите совместимый PyTorch на официальном сайте PyTorch и затем повторите
проверку ниже.

### 5.6. Проверка библиотек

```powershell
.\.venv\Scripts\python.exe -c "import pandas, openpyxl, sklearn, sentence_transformers, umap, hdbscan; print('Библиотеки установлены')"
.\.venv\Scripts\python.exe -c "import torch; print('PyTorch:', torch.__version__); print('CUDA:', torch.cuda.is_available()); print('GPU:', torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'CPU')"
```

Если первая команда заканчивается без ошибки, Python-часть установлена.
`CUDA: True` означает, что embeddings смогут считаться на NVIDIA GPU при
`embedding_device=auto`.

### 5.7. Перенос данных существующей установки

Этот шаг нужен только при переносе уже использовавшегося workflow. Для новой
установки без прежних задач его можно пропустить.

Сначала остановите Hermes и активные процессы workflow, затем перенесите в
новый проект:

- `knowledge/` — профили тем и накопленные примеры, включая SQLite и возможные
  служебные файлы WAL;
- нужные папки из `jobs/` — незавершённые задачи, состояние, метки и журналы;
- `files/` — исходники и проверенные пользователем книги;
- `outputs/` — ранее сформированные результаты.

Папку `jobs/<job>/` обязательно переносить, если для её результата ещё нужно
выполнить `/sknow`: идентификатор в листе `_Workflow` используется для поиска
соответствующей job.

Локальные модели можно перенести целиком в `../models/` вместо повторной
загрузки. Папку `.venv/` переносить между компьютерами не следует — создайте
новое виртуальное окружение и заново установите зависимости по инструкции
выше.

## 6. Установка локальной embedding-модели

### 6.1. Что такое embedding-модель

Embedding-модель — отдельная нейросеть-кодировщик. Она превращает каждую фразу
в числовой вектор, в котором смыслово похожие запросы расположены близко.

Это не основная текстовая LLM:

- E5 не ведёт диалог;
- не принимает бизнес-решения сама;
- не генерирует разметку в свободной форме;
- быстро и одинаково кодирует большие массивы;
- работает локально и не расходует токены облачной модели.

Workflow добавляет к каждой строке E5-префикс `query: `, получает
нормализованный вектор и использует скалярное произведение как cosine
similarity.

### 6.2. Поддерживаемые модели

По умолчанию используется:

- `multilingual-e5-base`;
- 768-мерные embeddings;
- модель точнее `small`, но медленнее и тяжелее;
- файл весов занимает примерно 1,1 ГБ.

Также поддерживается:

- `multilingual-e5-small`;
- 384-мерные embeddings;
- быстрее и экономнее;
- обычно менее точна на сложных смысловых границах.

Смена embedding-модели не заменяет качественную разметку и бизнес-границы.
Она улучшает геометрию похожести, но ошибки LLM в исходных метках всё равно
могут распространиться классификатором.

### 6.3. Структура каталогов моделей

Модели находятся не внутри Git-репозитория, а в соседнем каталоге
`../models`:

```text
parent/
├── models/
│   ├── multilingual-e5-base/
│   │   ├── 1_Pooling/
│   │   │   └── config.json
│   │   ├── config.json
│   │   ├── model.safetensors
│   │   ├── modules.json
│   │   └── tokenizer.json
│   └── multilingual-e5-small/        # необязательно
└── ai-seo-semantic-cleaner/
    ├── .venv/
    ├── seo_embeddings.py
    └── ...
```

### 6.4. Загрузка multilingual-e5-base

После установки `requirements.txt` выполните из корня проекта:

```powershell
.\.venv\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download(repo_id='intfloat/multilingual-e5-base', local_dir=r'..\models\multilingual-e5-base', allow_patterns=['config.json','modules.json','model.safetensors','sentence_bert_config.json','sentencepiece.bpe.model','special_tokens_map.json','tokenizer.json','tokenizer_config.json','1_Pooling/config.json'])"
```

Hugging Face нужен только для первоначальной установки модели. Во время
рабочей задачи код включает offline-режим, использует
`local_files_only=True` и не пытается скачивать файлы.

Можно скачать модель вручную и разместить её в том же каталоге. Обязательные
файлы проверяются до длительного запуска:

- `config.json`;
- `modules.json`;
- `model.safetensors`;
- `tokenizer.json`.

## 8. Установка интеграции Hermes

Python-workflow может запускаться вручную, но автоматический цикл рассчитан на
Hermes и проектные инструкции `AGENTS.md`.

### 8.1. Откройте правильную папку

В Hermes выберите корень клонированного проекта — папку, где одновременно
находятся:

- `AGENTS.md`;
- `seo_workflow.py`;
- `.venv/`;
- `files/`.

Если открыть родительскую или вложенную папку, относительные команды и
автоматическая загрузка инструкций работать не будут.

### 8.2. Установите skills

В репозитории находятся три skills:

- `hermes_customizations/skills/sclear/`;
- `hermes_customizations/skills/sknow/`;
- `hermes_customizations/skills/seo/seo-automation/`.

Импортируйте или скопируйте их в пользовательский каталог skills вашей версии
Hermes, сохранив каждую папку skill целиком. Путь пользовательских skills
зависит от способа установки Hermes. После копирования полностью перезапустите
Hermes.

`/sclear` проверяет наличие имени файла и темы и запускает новый workflow.
`/sknow` принимает ровно один проверенный XLSX и не запускает чистку заново.
`seo-automation` связывает команды с правилами `AGENTS.md`.

### 8.3. Установите патч автономного продолжения

Без патча модель может закончить ответ фразой «продолжаю работу» и фактически
остановиться до следующего сообщения пользователя.

Патч:

- активируется только в проекте с маркером
  `HERMES_SEO_AUTOPILOT` в `AGENTS.md`;
- проверяет последнее `jobs/<job>/state.json`;
- не запускает команды самостоятельно;
- добавляет внутренний запрос продолжить, только если state machine ещё не
  достигла `stop` или `blocked`;
- ограничена 30 автоматическими nudges.

Если Hermes установлен из Git рядом с этим проектом, перейдите в корень Hermes
и сначала проверьте применимость патча:

```powershell
git apply --check ..\ai-seo-semantic-cleaner\hermes_customizations\patches\hermes-seo-autopilot.patch
```

Затем примените его:

```powershell
git apply ..\ai-seo-semantic-cleaner\hermes_customizations\patches\hermes-seo-autopilot.patch
Copy-Item ..\ai-seo-semantic-cleaner\hermes_customizations\patches\seo_autopilot_stop.py .\agent\seo_autopilot_stop.py
```

Патч изменяет `agent/conversation_loop.py` и
`agent/turn_finalizer.py`, а также требует файл
`agent/seo_autopilot_stop.py`.

Перед изменением установленного Hermes сохраните резервную копию. Если
`git apply --check` сообщает конфликт, не применяйте патч принудительно:
версия Hermes отличается, и места интеграции нужно адаптировать к её текущему
коду.

После установки патча перезапустите Hermes.

### 8.4. Использование другой текстовой модели или harness

Никакой API-конфигурации конкретной LLM в Python-скриптах нет. Модель выбирается
в Hermes или другом harness.

Другой агентный harness должен:

1. загрузить `AGENTS.md`;
2. работать из корня проекта;
3. вызвать:

   ```text
   "./.venv/Scripts/python.exe" "./seo_workflow.py" next --input "<file>" --topic "<topic>" --quiet
   ```

4. выполнять точный текст поля `command` из JSON;
5. заполнять только предложенные компактные поля меток;
6. снова вызывать `next --job "<job>" --quiet`;
7. остановиться только при `status=stop`, `status=blocked` или
   `status=running`.

Обычный чат без доступа к терминалу не может автономно выполнить workflow,
даже если сама текстовая модель достаточно качественная.

## 9. Полная последовательность workflow

### Этап 1. Команда `/sclear`

Skill проверяет, что переданы:

- ровно один файл;
- непустое описание темы.

Затем вызывается `seo_workflow.py next`. Это главный контроллер. Сама LLM не
решает, какой скрипт запускать следующим: контроллер читает состояние и
возвращает одну разрешённую команду.

### Этап 2. Инспекция и создание job

`seo_prepare.py`:

1. находит файл в `files/`;
2. определяет формат, кодировку, разделитель, лист и колонку запросов;
3. определяет необязательную колонку частотности;
4. удаляет пустые значения;
5. нормализует регистр, `ё/е`, пробелы и пунктуацию;
6. объединяет одинаковые нормализованные фразы;
7. сохраняет первую исходную формулировку и номер исходной строки;
8. учитывает количество дублей и частотность при выборе приоритетов;
9. создаёт репрезентативную выборку;
10. создаёт уникальный ASCII `workflow_job_id`;
11. записывает job на диск.

Для CSV/TSV подготовка идёт потоково частями по 50 000 строк. В памяти
удерживается ограниченный reservoir, частотные строки и примеры лексических и
двухсловных структурных семейств. Весь большой CSV на подготовительном этапе
не загружается.

Репрезентативность строится из:

- наиболее частотных и повторяющихся запросов;
- длинных запросов;
- представителей символьных TF-IDF-микрокластеров;
- ограниченного набора реальных строк для покрытия частотных и
  среднечастотных intent-семейств;
- случайной части с фиксированным `random_state=42`.

По умолчанию рабочая выборка ограничена 800 строками.

Создаются:

- `jobs/<job>/inspection.json`;
- `jobs/<job>/job_config.json`;
- `jobs/<job>/model_labels.xlsx`;
- `jobs/<job>/intent_family_candidates.json`;
- `jobs/<job>/state.json`.

Seeds не нужно писать вручную. После первых реальных меток workflow сам
формирует тематические seeds. Класс `garbage` не создаётся искусственно, если
мусора в данных нет.

### Этап 3. Подключение сохранённых знаний

Для ядер больше 500 строк `seo_prepare.py` проверяет локальную базу знаний.
Если существует профиль с тем же нормализованным ключом темы, загружается до
150 сбалансированных примеров, но не больше примерно трети рабочей выборки.

Прошлые знания являются вспомогательными:

- текущие метки задачи имеют вес `1.0`;
- прежние метки модели — `0.35`;
- исправленные человеком примеры — `0.80`.

Для ядер до 500 фраз старые примеры не подмешиваются: модель размечает весь
текущий файл напрямую.

### Этап 4. Первичная разметка

LLM получает пакеты до 50 строк. Для каждой строки она возвращает:

- `commercial` — поиск, выбор или получение конкретного предложения/результата:
  товар, услуга, исполнитель, вакансия, работодатель, аренда, запись, заявка или
  другая конверсия; явное слово «купить» не обязательно;
- `informational` — инструкция, диагностика, справка, обзор, отзыв,
  сравнение, объяснение;
- `garbage` — запрос вне заявленной бизнес-темы.

Один контракт действует во всех пакетах задачи и не может меняться по ходу
разметки. Для двусторонних площадок обе стороны относятся к коммерческому
интенту: поиск вакансии соискателем и найм сотрудника работодателем являются
конверсионными запросами. Справка об обязанностях профессии остаётся
информационной.

Минимальная стартовая цель — 150 реальных меток либо все строки, если выборка
меньше.

Модель возвращает только:

```text
SampleID|label|confidence
```

Фразы повторно в команду импорта не вставляются. Это сокращает контекст и
предотвращает повреждение JSON длинными строками.

### Этап 5. Режим до 500 фраз

Если в ядре не более 500 уникальных запросов, LLM размечает каждый запрос.
Обученный классификатор всё равно используется как часть общей обработки, но
решения не экстраполируются с маленькой выборки на неизвестные строки.

### Этап 6. Priority review

Для более крупных ядер контроллер проверяет, получили ли метки наиболее
важные представители выборки. Неразмеченные приоритетные строки отправляются
LLM раньше обычного active learning.

### Этап 7. Аудит лексических и структурных семейств

До массовой классификации система находит как отдельные семейства слов, так и
частотные двухсловные структуры. Структуры строятся также через короткие
служебные слова: например, из «заявление на работу» извлекается связь между
«заявление» и «работа», несмотря на предлог «на». Вопросительные структуры
дополнительно приоритизируются для модельной проверки, но сами вопросительные
слова никогда не назначают класс. LLM получает до 20 семейств за пакет вместе
с восемью контекстно разнообразными реальными примерами. Примеры выбираются по
всему файлу, а не берутся из его первых строк.

Из общего лимита кандидатов часть мест зарезервирована за среднечастотными
семействами, которые раньше могли быть вытеснены наиболее частыми словами.
Названия документов — например, заявление, анкета, резюме, справка, договор,
образец и бланк — имеют приоритет только при обнаружении. Код не назначает им
информационный интент автоматически: фактический класс определяет LLM по
полным фразам и контексту текущей темы.

Так отдельно рассматриваются конструкции, эквивалентные «какую работу»,
«какую работу выполняет» и «какие вакансии», вместо попытки назначить один
интент слову «водитель». Конкретные структуры извлекаются из текущего файла, а
не из тематического словаря в коде.

LLM назначает семейству:

- `commercial`;
- `informational`;
- `neutral`.

Решающий класс назначается только тогда, когда само семейство устойчиво
определяет интент. Названия брендов, моделей, продуктов, профессий, общие
существительные и слабые вопросительные слова должны оставаться `neutral`.
Python дополнительно переводит небезопасное одиночное лексическое семейство в
`neutral`, даже если LLM ошибочно назвала его коммерческим или информационным.
Проверенная многословная структура при этом может остаться решающей.

Подтверждённые семейства становятся ограниченными тематическими сигналами. Они
могут уточнить пограничное решение классификатора, но не перебивают встречный
сильный маркер, противоположное семейство или уверенное предсказание по полной
фразе. Конфликты автоматически включаются в intent-аудит и `Human review`.
Поэтому один широкий корень слова не может изменить интент всех содержащих его
фраз. Слабые вопросительные семейства принудительно остаются `neutral`.

### Этап 7.1. Обязательная проверка покрытия семейств

Одного семейного правила недостаточно для обучения классификатора: уверенно
ошибочное предсказание может не попасть в область, где разрешена осторожная
коррекция правилом. Поэтому `seo_prepare.py` резервирует в тех же 800 строках
до 50 реальных представителей обнаруженных семейств. Это не увеличивает
размер рабочей выборки.

После первичной калибровки контроллер проверяет эти строки. Если среди них
остались неразмеченные, команда `family-coverage-review` отдаёт LLM один
короткий обязательный пакет. Для документальных понятий резервируется несколько
разнообразных контекстов, чтобы модель могла отличить поиск образца документа
от реального действия подачи заявки. Полученные метки входят непосредственно
в обучение Python-классификатора. Пока пакет не размечен, массовый запуск не
начинается.

### Этап 8. Создание тематической политики

LLM получает компактный контекст из уже размеченных строк и создаёт:

- явные коммерческие прототипы;
- неявные коммерческие структуры без слов «купить» и «цена»;
- информационные прототипы;
- сильные коммерческие сигналы;
- сильные информационные сигналы;
- слабые вопросительные сигналы;
- широкие релевантные прототипы;
- сложные отрицательные примеры.

Политика генерируется заново для текущей темы. В коде нет постоянного списка
автомобильных, медицинских, кадровых или других тематических маркеров.

Слабые слова вроде «как», «где», «сколько» сами класс не меняют. «Где купить»
и «сколько стоит» остаются коммерческими благодаря сильному транзакционному
сигналу; «как установить» или «почему сломалось» получают информационный
сигнал.

Если слабый вопрос присутствует без коммерческого сигнала, workflow уменьшает
необходимое преимущество информационной вероятности с обычных `0.12` до
`0.02`. Это не словарное правило для русского языка: конкретные слабые,
коммерческие и информационные сигналы создаёт LLM для текущей темы и языка.
Вопросительные строки без достаточного контекста отдельно попадают в active
review и `Human review`.

Перед сохранением сильных сигналов Python отклоняет wildcard с основой короче
четырёх символов и сигналы, которые противоречат достаточному числу уже
размеченных примеров. Поэтому короткая маска не должна случайно совпадать с
брендом, моделью или другим значением слова. Отклонённые сигналы возвращаются
LLM для замены более точным словом, длинной основой или многословной
конструкцией.

Синтетические intent-прототипы входят в обучение с весом `0.75`.
Синтетические релевантные и отрицательные boundary-примеры имеют вес `1.0`,
но не считаются строками исходного ядра.

### Этап 9. Аудит релевантности

LLM получает смесь:

- смысловых выбросов;
- строк около границы `garbage/relevant`;
- приоритетных запросов;
- представителей разных микрокластеров.

По умолчанию выполняется не менее трёх и не более шести relevance-аудитов.
Дополнительные пакеты прекращаются, если:

- два последних пакета почти не нашли нового мусора;
- либо накоплено достаточно реальных garbage-примеров.

Фиксированная доля мусора не требуется. Если ядро чистое, LLM не должна
превращать релевантные запросы в мусор ради квоты.

### Этап 10. Аудит commercial/informational

Не менее двух пакетов проверяют фразы около границы коммерческого и
информационного интента. Это особенно важно для похожих конструкций, где одно
слово меняет намерение пользователя.

### Этап 11. Аудит конфликтов политики

Отдельный пакет проверяет строки, где обученный классификатор и сильные
тематические сигналы расходятся. Политика может быть уточнена один раз; workflow
не запускает бесконечное переписывание маркеров.

После завершения обязательных аудитов и active learning политика один раз
пересматривается на расширенной разметке. Это важно, потому что первая версия
создаётся рано и ещё не видит всех пограничных конструкций. Новая версия не
принимается безусловно: Python сравнивает покрытие и ложные срабатывания на
реальных проверенных строках. При регрессии сохраняется предыдущая политика.

### Этап 12. Active learning

После обязательных аудитов Python выбирает наиболее полезные неразмеченные
строки:

- низкая уверенность;
- близость вероятностей commercial и informational;
- близость к порогу мусора;
- конфликт сильного сигнала и классификатора;
- смысловой выброс;
- представитель важного кластера.

Обычная цель — около 300 меток. Для грязного ядра цель повышается до 500,
если доля мусора в разметке превышает 15% либо накоплено не менее 30 реальных
garbage-примеров.

### Этап 13. Проверка готовности

Перед массовым запуском контроллер проверяет:

- для ядра больше 500 строк — минимум по 30 текущих реальных commercial и
  informational примеров; сохранённые знания прошлых задач эту квоту не
  закрывают;
- отсутствие конфликтующих меток одной фразы;
- покрытие приоритетных строк;
- наличие тематических прототипов и сигналов;
- прохождение финальной регрессионной проверки политики;
- корректность job;
- отсутствие посторонних Python-скриптов в корне;
- отсутствие уже работающего процесса.

Если один intent представлен недостаточно, workflow продолжает ограниченную
калибровочную разметку с явным контрактом классов. Если вся выборка исчерпана,
массовый запуск блокируется: система не обучает классификатор на 10–12 строках
миноритарного класса и не изобретает искусственные метки.

Если проверка не пройдена, workflow не начинает дорогой этап и возвращает
конкретную причину.

### Этап 14. Выбор режима

`run-auto` читает число нормализованных фраз из `inspection.json`:

- меньше 100 000 — стандартный режим;
- 100 000 и больше — крупный режим.

Выбор не зависит от того, XLSX это или CSV. Большой XLSX временно преобразуется
самим workflow в job-local TSV только с фразой и частотностью. Временный TSV
удаляется и при успехе, и при ошибке.

### Этап 15. Локальные embeddings

`seo_embeddings.py`:

1. проверяет локальные файлы модели;
2. запрещает сетевую загрузку;
3. выбирает CUDA при `embedding_device=auto` и доступном PyTorch CUDA;
4. иначе использует CPU;
5. кодирует фразы пакетами, по умолчанию по 256;
6. возвращает `float32` нормализованные vectors.

Embedding-модель видит все фразы, но работает локально. Основная LLM видит
только выборки.

### Этап 16. Двухступенчатая классификация

`seo_pipeline.py` обучает две Logistic Regression.

Первая ступень:

```text
relevant ↔ garbage
```

Вторая ступень применяется только к релевантной части:

```text
commercial ↔ informational
```

Разделение не позволяет редкому классу мусора слишком сильно искажать границу
между коммерческими и информационными запросами.

Признаки состоят из:

- E5 embeddings;
- символьного TF-IDF по n-граммам длиной 3–5;
- тематических прототипов;
- проверенных семейств и сильных сигналов.

Символьный TF-IDF помогает учитывать словоформы, опечатки, артикулы, марки и
структурно похожие запросы. Embeddings дают смысловую близость.

Если реальных данных достаточно, garbage-порог калибруется по out-of-fold
прогнозам. Цель — сохранить точность garbage не ниже 80% и не превысить 5%
ложного удаления релевантных примеров. Если безопасная калибровка невозможна,
используется настроенный порог `0.45`.

### Этап 17А. Стандартная кластеризация

Для каждого из двух релевантных интентов отдельно:

1. embeddings уменьшаются UMAP;
2. HDBSCAN находит плотностные группы без заранее заданного числа кластеров;
3. TF-IDF выбирает характерные слова;
4. формируется читаемое название кластера;
5. выбросы получают `Unclustered`.

UMAP и HDBSCAN работают со всем массивом конкретного интента в памяти, поэтому
этот режим не используется для ядер от 100 000 строк.

### Этап 17Б. Крупномасштабная кластеризация

Большой файл обрабатывается частями, по умолчанию по 50 000 строк:

1. часть читается с диска;
2. считаются embeddings;
3. выполняется классификация;
4. результат сохраняется в `parts/part-XXXXXX.csv.gz`;
5. embeddings временно сохраняются в `.embedding-cache`;
6. из данных выбирается детерминированная репрезентативная выборка;
7. MiniBatchKMeans строит до 80 центроидов на каждый интент;
8. каждая оставшаяся фраза назначается ближайшему центроиду;
9. создаются сводка и очередь неоднозначных строк;
10. временный embedding-кэш удаляется.

Это приближённая кластеризация: она масштабируется лучше глобального
UMAP/HDBSCAN и не требует держать миллионы vectors в RAM одновременно.

### Этап 18. Relevance-аудит крупных кластеров

После предварительного крупного запуска LLM получает до 30 кластеров за пакет.
Для каждого показаны:

- название;
- размер;
- средняя вероятность мусора;
- центральный представитель;
- частотный представитель;
- подозрительный выброс;
- пограничная фраза.

LLM назначает кластеру `relevant`, `garbage` или `mixed` и отдельно
размечает рискованные представители. Затем Python консервативно применяет
решения и, при достаточном числе примеров, обучает постклассификатор
внутрикластерных выбросов.

Спорные строки не удаляются автоматически. Для распространения garbage-решения
требуются безопасные показатели: высокая ожидаемая точность и низкая доля
ложного удаления релевантных строк.

### Этап 19. Экспорт

Стандартный и крупный режимы создают одинаковый пользовательский Excel:

- `Commercial clusters`;
- `Informational clusters`;
- `Garbage`;
- `Human review`;
- `Cluster summary`;
- `_Workflow`.

`_Workflow` — технический лист. В нём находятся:

- `Workflow Job ID`;
- job;
- тема;
- исходный файл;
- режим обработки.

Он нужен, чтобы `/sknow` нашёл правильную job даже при нескольких завершённых
задачах. Не удаляйте и не изменяйте `Workflow Job ID`.

Коммерческий и информационный листы содержат только:

- `Phrase`;
- `Search Volume`;
- `P(commercial)`;
- `P(informational)`;
- `P(garbage)`;
- `Cluster`;
- `Source Row`.

`Garbage` содержит:

- `Phrase`;
- `Search Volume`;
- `P(commercial)`;
- `P(informational)`;
- `P(garbage)`;
- `Source Row`.

`Human review` содержит:

- `Phrase`;
- `Search Volume`;
- `Predicted Intent`;
- `P(commercial)`;
- `P(informational)`;
- `P(garbage)`;
- `Cluster`;
- `Review reason`;
- `Correct Intent`;
- `Reviewer Notes`;
- `Source Row`.

Вероятности округляются до четырёх знаков после запятой. Они полезны для
сортировки и дополнительной ручной проверки: чем меньше разница между
`P(commercial)` и `P(informational)`, тем менее устойчиво определён интент;
высокая `P(garbage)` у релевантной строки указывает на границу тематической
релевантности. Это диагностические оценки классификатора, а не гарантированная
точность решения.

`Cluster summary` содержит:

- `Intent`;
- `Cluster`;
- `Phrases`;
- `Total Search Volume`.

Если один класс превышает лимит Excel в 1 048 575 строк, создаются
продолжающие листы с числовым суффиксом. Полные крупные данные также остаются
в сжатых CSV-частях, потому что гигантский Excel неудобен даже при технически
допустимом числе строк.

### Этап 20. Состояние и длительные процессы

После каждого этапа обновляется `jobs/<job>/state.json`. Поэтому новый чат
может вызвать `next --job` и продолжить с диска, не восстанавливая всю
переписку.

Перед длинным запуском создаётся `.seo_run.lock.json`. Пока процесс активен:

- повторный `run` не запускается;
- `next` возвращает `status=running`;
- агент не должен опрашивать процесс в цикле.

Длинные сообщения библиотек перенаправляются в:

- `jobs/<job>/logs/run.log`;
- либо `jobs/<job>/logs/run_large.log`.

LLM получает только компактный итог: статус, путь, число строк и длительность.
Это защищает контекст от progress bar, предупреждений и миллионов строк.

## 10. Рабочие файлы после завершения

`jobs/<job>/` полезна для:

- продолжения незавершённой задачи;
- просмотра конфигурации;
- диагностики по журналам;
- аудита использованных меток.

Безопасная очистка только временных файлов:

```powershell
.\seo.ps1 cleanup --job "<job>"
```

Эта команда не удаляет всю job. Она удаляет только известные временные
каталоги, Python-кэши, временные файлы и неактивный lock.

## 11. Используемые библиотеки

| Компонент | Для чего используется |
|---|---|
| Python | Контроллер, обработка данных, состояние и экспорт |

## 12. Ручные диагностические команды

Обычно достаточно `/sclear` и `/sknow`. Для диагностики можно использовать
PowerShell-обёртку.

Статус job:

```powershell
.\seo.ps1 status --job "<job>" --compact
```

Следующее действие state machine:

```powershell
.\seo.ps1 next --job "<job>" --quiet
```

Список сохранённых тем:

```powershell
.\seo.ps1 knowledge --quiet
```

Знания конкретной темы:

```powershell
.\seo.ps1 knowledge --topic "<тематика>" --quiet
```

Проверка универсальной логики intent-семейств после изменения кода:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Удаление знаний темы является отдельной разрушительной операцией и требует
точного подтверждения нормализованного topic key:

```powershell
.\seo.ps1 forget --topic "<тематика>" --confirm "<topic-key>" --quiet
```

Не запускайте `seo_pipeline.py`, pandas-скрипты или произвольный
`python -c` для обхода state machine во время активной SEO-задачи. Основная
точка входа — `seo_workflow.py`.

## 13. Типичные проблемы

### Не найдена колонка запросов

Проверьте заголовок и лист XLSX. При нестандартном названии используйте:

```powershell
.\seo.ps1 prepare "<файл>" --topic "<тематика>" --phrase-column "<колонка>" --quiet
```

### Ошибка кодировки CSV

Поддерживаются UTF-8, UTF-8 BOM, CP1251 и CP866. Исходник не нужно
перекодировать вручную. Если файл имеет другую кодировку, экспортируйте его в
UTF-8 или CP1251.

### Модель embeddings не найдена

Проверьте структуру `../models/multilingual-e5-base/` и обязательные файлы.
Workflow намеренно не скачивает модель во время задачи.

### CUDA показывает False

Проверьте:

```powershell
nvidia-smi
.\.venv\Scripts\python.exe -c "import torch; print(torch.__version__); print(torch.cuda.is_available())"
```

Если PyTorch установлен без CUDA, переустановите вариант из
`requirements-cuda.txt`.

### Процесс кажется зависшим

Не запускайте его повторно. Проверьте:

- возвращал ли `next` `status=running`;
- существует ли активный lock;
- обновляется ли `jobs/<job>/logs/run.log` или `run_large.log`;
- пришло ли уведомление о завершении фонового процесса.

Повторный запуск одновременно может испортить промежуточные результаты.

### Модель постоянно просит написать «продолжи»

Проверьте:

- открыт ли корень проекта;
- загружен ли `AGENTS.md`;
- установлены ли все три Hermes skills;
- применён ли патч autopilot;
- перезапущен ли Hermes после установки.

### Результат слишком большой для Excel

Для крупных ядер основными полными данными являются
`outputs/<job>/large/<input>/parts/*.csv.gz`. Excel предназначен для работы,
фильтрации и ручной проверки. При превышении лимита строк создаются
дополнительные листы.

## 14. Обновление проекта

Перед обновлением сохраните пользовательские данные:

- `files/`;
- `outputs/`;
- нужные `jobs/`;
- `knowledge/seo_knowledge.sqlite3`;
- локальные модели из `../models/`.

Затем:

```powershell
git status
git pull
.\.venv\Scripts\python.exe -m pip install --upgrade -r requirements.txt
```

Для CUDA повторно примените:

```powershell
.\.venv\Scripts\python.exe -m pip install --upgrade -r requirements-cuda.txt
```

После обновления Hermes проверьте применимость autopilot-патча к новой версии.

## 15. Главное ограничение

Workflow не превращает классификацию в объективную истину. Итог зависит от:

- качества описания тематики;
- возможностей выбранной текстовой LLM;
- разнообразия исходной выборки;
- наличия реальных пограничных примеров;
- качества embedding-модели;
- ручной проверки и накопленных исправлений.

Лучший практический процесс:

1. точно описать бизнес-границы;
2. выполнить `/sclear`;
3. проверить `Garbage`, крупные кластеры и весь `Human review`;
4. импортировать исправления через `/sknow`;
5. использовать накопленные знания как помощь в следующем запуске, но не как
   безусловное правило.
